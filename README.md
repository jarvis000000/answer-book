# 答案之书

把《高性价比人生指南》的 657 条建议做成一个**能按你的处境检索**的问答工具。

你问「我是一个 45 岁女性，需要注意哪些身体健康方面的问题」，它从 657 条里挑出
乳腺癌筛查、宫颈癌筛查、骨密度检查，并告诉你每条的证据等级、性价比档、原始出处。

```
$ npm run ask -- "我是一个45岁女性，我需要注意哪些身体健康方面的问题"

问题  我是一个45岁女性，我需要注意哪些身体健康方面的问题
理解  年龄 中年 · 性别 female · 领域 健康
命中  265 条候选，展示前 6 条

1. 第 1 节第 18 条 30 岁以上女性做宫颈癌筛查，优先 HPV 检测
   [证据 A 级 · 性价比 高 · 口径 死亡率]
   说人话  印度农村那项试验里，一辈子只做过一次 HPV 检测的女性，
           死于宫颈癌的概率低约一半……
   标签    中年/青年/老年 · 女性专属 · 健康/安全 · 主题：癌症筛查
   为什么  领域命中：健康 · 年龄段贴合：中年、青年、老年 · 女性专属条目
```

---

## 它做什么

源书是**按性价比排序的一本书**，不是搜索引擎——657 条平铺在那里，你得自己找到跟你有关系的那几条。
这个项目补的就是这一步：**把「我的处境」和「这条建议」对上**。

具体做三件事：

1. **给每一条打标签**：年龄段、性别、领域、主题、人群。标签是规则算出来的，可复现、可 diff，也能人工覆盖。
2. **把你的人话问题解析成结构化条件**：从「45 岁女性」里读出 `年龄=中年`、`性别=female`，从「摔跤」里读出 `主题=跌倒与骨折`。
3. **按关键词 + 标签两路打分排序**：问得泛就靠标签排，问得具体就靠关键词排。

## 它不做什么

- **不改写原文。** 所有答案正文逐字来自源书，出处写到「第 X 节第 Y 条」。
- **不生成内容。** 连可选的 LLM 层也只参与「解析问题」和「给候选重排」两件事，一个字都不产出（见下文）。
- **不替代医生、律师、会计。** 沿用源书定位：给通用口径和方向，具体个案找人。

## 网页界面

```
npm run serve        →  http://127.0.0.1:5173
```

- **提问框始终吸附在顶部**，往下滚也不会跑掉；滚动时自动收成紧凑形态，把空间让给结果。
- **结果是一张张卡片**：证据等级用色点、性价比用三段小柱，不用读文字就能扫。
  点任意一张卡片弹出详情，完整展开成本 / 收益 / 备注 / 原始文献链接。
- **五种排序随时切换**：相关性 · 证据等级 · 性价比 · 成本最低 · 章节顺序。
  换排序**不改变「哪些条目相关」**，只改变先看哪几条——按等级排是在相关条目里挑 A 级，
  不会把整本书的 A 级都捞进来（有测试钉住这条）。
- **能看到全部相关条目**：默认首屏 12 条，下面标着「还有 N 条」，
  「显示更多」逐批展开，「展开全部」一次铺到底。顶部还会说明从多少条候选里挑出了多少条相关。
- **能按证据等级筛**：A / B / C 一键过滤。
- **日间 / 夜间**两套配色，首次访问跟随系统偏好。

界面本身零依赖，没有构建步骤，也不加载任何外部字体或 CDN——断网可用。

接口侧对应两个参数：`GET /api/ask?q=…&limit=…&sort=…`，
`limit` 上限 100（界面取 60），`sort` 取 `relevance` / `grade` / `ratio` / `cheap` / `section`。
`/api/meta` 返回可用的排序方式，界面直接照它渲染，不用两边各写一份枚举。

### 一键静态部署（暂挂 · 尚未实现）

> **这一节目前是占位说明，功能还没做。** 现在要用起来必须有一个 Node 进程在跑，
> 不能直接扔到 GitHub Pages 这类纯静态托管上。

想要的是：一条命令出一条 `dist/`，推到 GitHub Pages 就能用——不用服务器、不用联网。

**卡在哪**：检索跑在服务端。`/api/ask` 是 Node 进程现场算 BM25 和标签分的，
静态托管上没有这个进程。所以不是加个构建脚本的事，要把检索内核整个搬到浏览器里。

**大概要做的三步**：

1. **构建期预计算**：把倒排索引、文档长度、IDF 这些 BM25 需要的中间量导出成静态文件，
   别让浏览器每次现算——657 条现算一次要几百毫秒，还得先下载全文才能建索引。
2. **让检索模块同时能在两边跑**：`src/search/` 那套现在只用标准 API，本来就是环境无关的，
   主要改动是让索引从「构建期传进来」变成「运行时加载」。用 ES module 写的好处在这里体现。
3. **数据分两批下发**：一次全下 2.3 MB 对手机不友好。分两段的实测体积：

   | 内容 | 原始 | gzip |
   |------|------|------|
   | 全部字段（含来源、交叉引用） | 2358 KB | 670 KB |
   | 去掉来源等长字段 | 1412 KB | 491 KB |
   | **只留标题 + 标签 + 证据等级 + 性价比** | **207 KB** | **45 KB** |

   第一批只下 45 KB（gzip 后）就够跑完检索和排序，点开某一条时再去取那一条的完整正文。
   这个体积对静态托管完全没有压力。

**为什么现在没做**：本地起服务这条路已经够用（`npm run serve`，一条命令），
而静态化要动检索内核的加载方式，值得单独一轮做，不适合顺手塞进界面改版里。

## 快速开始

需要 Node.js 20 以上。零第三方依赖，不需要 `npm install`。

```bash
# 1. 把 Markdown 编译成带标签的结构化数据（改词表后要重跑）
npm run build

# 2. 命令行提问
npm run ask -- "一个6岁儿童有哪些建议和指南"
npm run ask -- --limit 10 "租房押金不退怎么办"
npm run ask -- --json "被公司裁员了能拿多少钱"     # 机读输出

# 3. 本地网页
npm run serve            # 打开 http://127.0.0.1:5173

# 4. 测试与评测
npm test                 # 73 条单元测试
npm run eval             # 32 条检索评测，报 hit@1 / hit@3 / hit@5 / MRR
```

不带参数运行 `npm run ask` 会进入交互模式，可以连续提问。

## 检索效果

`npm run eval` 的评测集（32 条标注用例，覆盖年龄段、健康、法律、财务、育儿、工作等场景）：

| 指标 | 数值 | 含义 |
|------|------|------|
| hit@1 | 81.3% | 第一条就是对的 |
| hit@3 | **96.9%** | 前三条里有对的——实际使用最在意的口径 |
| hit@5 | 100% | 前五条里有对的 |
| MRR | 0.886 | 第一条正确结果排名倒数的均值 |

排在第 5 位，前三位被讲「体检套餐」的条目占住。原因见下文「一个没解决的问题」。

## 标签体系

五个人工维护的维度，全部由词表命中决定，不用模型猜：

| 维度 | 取值 | 怎么定 |
|------|------|--------|
| `ages` 年龄段 | 婴儿 / 幼儿 / 学龄 / 青少年 / 青年 / 中年 / 老年 / 全龄 | 标题里的年龄数字 + 称呼词词表 |
| `gender` 性别 | female / male / any | **只看标题**，正文里的性别词多半是研究人群而不是受众 |
| `domains` 领域 | 健康 / 法律 / 财务 / 育儿 / 职业 …… 共 24 个 | 章节默认映射 ∪ 条目关键词 |
| `topics` 主题 | 疫苗 / 癌症筛查 / 租房买房 / 工伤 …… 共 44 个 | 词表命中 ∪ 章节映射 |
| `audiences` 人群 | 家长 / 老年人 / 打工人 / 程序员技术人 …… | 词表命中 ∪ 章节映射 |

源书自带的两个字段直接沿用，不重新定义：`grade`（证据等级 A/B/C）、`cost`（成本标签：钱/时间/毅力/收益/口径）。
性价比档 `ratio`（极高/高/一般）按上游规则现场合成：

```
成本分 = 权重(钱) + 权重(时间) + 权重(毅力)     权重：0/少/否=0，少/中/些=1，多/是=2
收益大 且 成本分 = 0            → 极高
收益大 且 成本分 ≤ 2，或 收益中 且 成本分 = 0 → 高
其余                            → 一般
```

### 词表放在哪儿

- `data/taxonomy.json` —— 标签体系的唯一真源。改这里就能改变全书的标签结果，改完跑 `npm run build`。
- `data/synonyms.json` —— 查询同义词表。见下文。
- `data/overrides.json` —— 人工覆盖。规则算错了就在这里改单条，不用动词表伤及无辜。

三者分开是有意的：**机器结论和人工判断各存一份**，重建时机器先算、人工后覆盖，
既能随时回退，也能随时看出哪些条目是人手动修过的。

## 匹配是怎么做的

### 1. 切分：中文二元组，不引分词词典

语料只有 657 条，查询都是短句。二元组（「幽门螺杆菌」→ 幽门/门螺/螺杆/杆菌）
对短文本检索的效果接近分词，而且不会因为词典缺词而漏召，还省掉了整个依赖。

### 2. 查询解析：先把套话删干净

「我是一个 45 岁女性，我需要注意哪些**方面的问题**」——这句里真正有检索价值的只有
「45 岁」「女性」「身体」「健康」，其余全是套话。中文没有词边界，套话会被切成
「是一」「康方」「面的」这类跨词边界的碎片。它们在全语料几乎不出现（IDF 反而最高），
一命中就把完全无关的条目顶上来（讲「聚光灯效应」的条目曾靠「检报」二字进了前十）。

所以检索前先做两步清洗：

- `QUERY_PHRASES` 整段删除提问套话
- `isFunctionOnly()` 丢掉整段由功能字组成的残片（「我要做」「要做」）

### 3. 碎片过滤：出现不到 3 篇的词一律丢掉

真实用词一定会在语料里反复出现。「检报」「告说」「说血」这类碎片全语料只出现 1 到 2 次，
但它们 IDF 最高、误伤力最强。判据就是文档频率。

代价是**真词也会被误伤**：「裁员」在这本书里只出现 1 次（书写的是「被裁」「辞退」），
「摔跤」只出现 1 次（书写的是「跌倒」）。这类鸿沟靠 `data/synonyms.json` 人工补上——
中文二元组切分无法自己发现「裁员」和「辞退」是一回事。

同义词有一条关键规则：**书里本来就说这个词时不翻译**。判据是「这个词切出来的二元组在语料里够常见」。
「被裁」翻成「解除劳动合同」看着合理，实际会把 合同、劳动、解除 三个书里的高频词
全塞进查询，问「怎么领失业金」的条目会被第 19 节讲劳动合同的条目顶下去。

### 4. 排序：关键词和标签按查询的具体程度动态配比

```
最终分 = 关键词分 × w + 标签分 × (1 − w)
```

`w` 不是常数，取决于**这条查询带了多少可区分的信息**（查询里最罕见那个词的 IDF）：

- 问「幽门螺杆菌要不要查」——有罕见词，关键词说了算，`w = 0.70`
- 问「我该注意什么」——全是常见词，关键词几乎没有区分度，`w = 0.35`，让标签主导

标签分内部：领域 0.28 / 年龄 0.30 / 性别 0.20 / 主题 0.12 / 人群 0.10。
年龄和性别合计接近六成——这本书是按「谁该做什么」组织的，
「这条是不是写给我的」比「这条属于哪个大类」更能决定该不该排前面。

两个细节：

- **BM25 用压缩式归一化**（`2·raw/(raw+max)`）而不是线性除以最大值。
  线性归一化会让那个「碰巧多命中一个词」的条目独拿 1.00、把别人压到 0.6 以下；
  而中文短查询里多命中一个词往往只是运气。压缩后高分条目彼此靠拢，名次交还给标签分。
- **提问者自报身份会被加成**。说了「45 岁女性」，那么正好是「中年 + 女性专属」的条目 ×1.12；
  性别不匹配的条目 ×0.05，压到候选末尾。

### 5. 三级安全兜底

急症、自杀念头、正在进行的法律程序这三类问题，先给「马上做什么」，再列条目——
和源书自带的 skill 处理一致。这三类不能拿性价比排序去回答。

## 接入 LLM（可选，默认关闭）

设计上把 LLM 放在**最外围**：它只做两件事——把问题解析得更准、把候选重新排序。
答案正文永远来自本地 657 条，一个字都不由模型生成。

这么做是因为源书的全部价值在于「每个数字都能指回原始文献」。
一旦让模型改写或补全，这个价值立刻归零，而且会以最难发现的方式出错（编出来的 DOI、记错的百分比）。

```bash
export ANSWER_BOOK_LLM_BASE=http://127.0.0.1:8080/v1   # OpenAI 兼容接口
export ANSWER_BOOK_LLM_KEY=sk-xxx                       # 本地网关可留空
export ANSWER_BOOK_LLM_MODEL=gpt-4o-mini
```

没配这三个变量时走纯规则实现——**这不是降级路径，是默认路径**。
配了但接口挂了，自动退回规则结果（有测试覆盖），检索不会停摆。
模型自造的标签名（不在 `taxonomy.json` 的领域列表里）会被直接丢弃。

代码在 `src/llm/adapter.mjs`，接口是 `createRulePlanner()` 和 `createLLMPlanner()`，
两者都实现 `plan(question)`，可以直接替换。

## 关于「一个没解决的问题」

问「体检报告说血压高，我要做什么」，正确条目排在第 5 位。

原因是这句话里「体检报告说」占了两个查询词（体检、报告），而真正想知道的「血压」只占一个。
讲体检的条目命中两个词，讲血压的条目只命中一个，BM25 天然偏向前者。

试过的修法都不理想：加大标签权重会连带弄坏其他用例；
按位置给查询词加权（假设重要信息在后面）在中文里站不住脚；
把「体检报告」合并成一个词仍然不改变两组词的数量对比。

**这一条留着没修**，是因为不想为了它去加一条只在特定句式下生效的启发式规则——
那种规则在评测集上能涨一个点，在真实使用里会以没人能解释的方式弄坏别的地方。
当前它在 top-5 里，用户滚动一下就能看到。
